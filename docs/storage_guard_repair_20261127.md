# 模型空闲释放修正与实际验证

用户于2026年11月27日明确要求先解决空间保护停止。本次仅修改项目的模型生命周期和诊断记录；不改分页、分区、BitLocker、系统环境或已安装依赖，不清理个人资料，不降低C至少5GiB、D至少10GiB及模型活动期间C下降1GiB的保护条件。

## 发现与修正

原模型在成功返回搜索后一直驻留。保护代码保留首次加载前的C空间基线，持续跨整个驻留期间比较系统盘空间。因此，模型空闲时其他应用或Windows分页的变化也可能触发停止。旧日志缺乏资源采样，无法把那次瞬时变化具体归因于某个应用或文件，不能断言旧停止完全是误报。微软说明系统管理分页可随提交需求增长：[官方说明](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/how-to-determine-the-appropriate-page-file-size-for-64-bit-versions-of-windows)。本次没有更改该系统设置。

新演示配置在最后一次成功的AI搜索后空闲60秒，释放健康模型工作器；只在下一次明确的AI搜索时重新加载。正在加载或搜索时不因空闲计时而中断，也不在连续活动期间反复重置空间基线。新的资源停止与意外退出持久记录在D，不能伪装成正常空闲释放、通过服务重启清掉，或者自动重试。词法检索、目录、地图和评分不需要模型驻留。

旧失败文件outputs/model_stop_checkpoint_20261127.json原件保留。Start-Demo.ps1仅接受本次已成功验证且源码/数据哈希完全匹配的新配置回执，并在有更新停止记录时拒绝重新启动模型。原通用服务默认仍为空闲自动释放关闭，历史FP32实验与评分不变；本地演示入口明确选FP16、60秒空闲释放和独立停止记录。读取状态、浏览地点不会预加载模型。

## 单次有上限的实机检查

准备并记录具体新方案后，验证脚本仅进行两次冷加载，中间和结束均检查健康空闲释放；任一步失败就停止，不自动重试。原失败配置没有重放。批准范围、源码绑定、消费记录与真实输出位于outputs/residency_repair_20261127。

Windows虚拟环境启动器和真正的Python模型子进程是不同PID。runtime_telemetry中的worker_*为启动器根PID本身，不能拿其约1.3MB提交量当作模型总占用。本次另保存两份完整进程树：最大捕获私有提交量约3.31GB（约3.08GiB），驻留内存约1.64GB；私有提交与实际物理RAM不同。退出复核为释放后的检查，不声称TerminateProcess调用瞬间所有资源同步消失。资源原始记录只在D，不含新人工评分。

407项工作测试通过13.27秒。新增测试验证空闲/活动互斥、保护优先于健康释放、失败跨服务重建保留、意外退出不当作健康空闲，以及源码回执不匹配/新失败时拒绝重新启动。合成测试不作为真实模型或评价数据。

入口复查另发现当前令牌无法可靠读取Windows CIM网络枚举；旧的静默端口枚举可能漏掉已运行服务。已改为Python标准库直接探测127.0.0.1:8770，无法确认时拒绝启动；实际重复入口测试返回“already listening”，未创建模型。一次词法入口探测造成的本任务重复测试服务已核实身份后停止，原修正服务保留。这项仅入口检测的后续修改不改变模型运行源码、参数或两轮实测结果；原实测回执另存validation_model_check_original.json，后续入口校验及新入口哈希单独记录在回执中，没有追加模型加载。

## 当前使用与限制

刷新 http://127.0.0.1:8770/ ，选择BGE-M3后搜索即可。模型空闲时为not_loaded，不是故障；首次或释放后的第一条搜索需要重新加载，本轮观察约39–62秒，连续搜索更快。关闭再恢复入口仍为Start-Demo.ps1，先查监听避免重复。旧论文/PPT中“当前暂停”描述属于修正前交付检查点，最新运行状态以本报告和实际API为准。

这解决了成功搜索后无限驻留的程序问题，并在两轮加载与释放中恢复了AI搜索；不代表对任意应用负载、长时间运行或所有用户输入的稳定性保证。如果系统实际低于保护线，仍应停止并记录。C没有因此恢复到20或30GiB；没有新增模型训练、依赖下载、人工判断或效果指标。
